จองสต็อก ตัดสต็อก คืนสต็อก — เขียนลง Table ไหนบ้าง

ไล่โค้ดจริงใน b1dx-oms-fulfillment-api เพื่อดูว่า handler ตัวไหนทำงานเมื่อไหร่ แล้วมีการ INSERT/UPDATE ลง table ใน schema wms ตามลำดับใด สำหรับ 3 flow หลัก: จอง / ตัด / คืนสต็อก

Schema: wms · oms แหล่งข้อมูล: b1dx-oms-fulfillment-api ตรวจเมื่อ: 2026-08-11
!

ยืนยันจาก Source Code ไม่ใช่ข้อมูลจริง

wms.stock_reservations และ wms.stock_movements ใน database ตอนนี้ ยังไม่มีข้อมูลเลย — ยังไม่มี order ไหนวิ่งผ่าน flow จอง/ตัด/คืนจริง ลำดับด้านล่างทั้งหมดตรวจสอบจาก source code ของ handler โดยตรง ไม่ใช่จาก transaction ที่เกิดขึ้นจริง

01 จองสต็อก 3 การเขียน 02 ตัดสต็อก 3 การเขียน 03 คืนสต็อก — ปล่อยจอง & รับคืนของจริง 2 + 3 การเขียน
01

จองสต็อก Reserve

TriggerOrder 200 → 300

ReserveStockSideEffectHandler ล็อค lot ที่จะจอง ทำเครื่องหมายว่าจองแล้ว และปักหมุดว่าจองไว้กับ lot/location ไหน — ของยังไม่ได้เคลื่อนที่จริง

1
wms.stock_balances UPDATE
reserved += qty
→
2
wms.stock_reservations INSERT
สร้างแถวใหม่ status = reserved
→
3
wms.stock_reservations UPDATE
ปักหมุด lot/location ที่จองไว้
รายละเอียดการเขียน — จองสต็อก
#Tableคำสั่งผลลัพธ์
1wms.stock_balancesUPDATEreserved = reserved + qty ภายใต้ row lock แบบ FOR UPDATE
2wms.stock_reservationsINSERTสร้างแถวใหม่ status = 'reserved'
3wms.stock_reservationsUPDATEเซ็ต internal_lot_id / internal_location_id — ระบุว่า balance แถวไหนรองรับการจองนี้
ขั้นถัดไป (ไม่ได้เกิดจาก order transition โดยตรง แต่เกิดตอนเริ่ม pick session): Allocate จะ INSERT wms.stock_reservation_allocations แล้ว UPDATE wms.stock_reservations SET status = 'allocated'
02

ตัดสต็อก Deduct

TriggerOrder 490 → 500

DeductStockSideEffectHandler commit การจองตอนยืนยันจัดส่ง — เป็นจุดที่ on_hand ลดลงจริง และเป็น flow เดียวที่บันทึก movement ไว้

1
wms.stock_balances UPDATE
on_hand −= qty
reserved −= qty
→
2
wms.stock_movements INSERT
movement_type = 'ship'
→
3
wms.stock_reservations UPDATE
สถานะ = committed
รายละเอียดการเขียน — ตัดสต็อก
#Tableคำสั่งผลลัพธ์
1wms.stock_balancesUPDATEon_hand = on_hand - qty, reserved = GREATEST(0, reserved - qty)
2wms.stock_movementsINSERT1 แถวต่อ lot, movement_type = 'ship', reference_type = 'order'
3wms.stock_reservationsUPDATEstatus = 'committed' — สถานะสิ้นสุด การจองนี้เสร็จสมบูรณ์
flow นี้เป็น flow เดียว ในทั้ง 3 แบบ ที่มีการ INSERT ลง wms.stock_movements จริง — ทั้งจองและปล่อยจองไม่แตะตารางนี้เลย
03

คืนสต็อก Return

2 เส้นทางแยกกันดูรายละเอียดด้านล่าง

"คืนสต็อก" ครอบคลุม 2 เส้นทางโค้ดที่ไม่เกี่ยวข้องกัน ขึ้นอยู่กับว่าของออกจากคลังไปแล้วหรือยัง

3a · ปล่อยจอง — ยกเลิกออเดอร์ก่อนส่งของ

ReleaseStockSideEffectHandler ปล่อยการจองที่ยังไม่เคยถูกตัดจริง มีแค่ reserved ที่ขยับ — ไม่มีของจริงต้องคืนกลับ

wms.stock_balances UPDATE
reserved −= qty
ไม่แตะ on_hand
→
2
wms.stock_reservations UPDATE
สถานะ = released
→
–
stock_movements
ไม่ถูกเขียน

3b · คืนของจริง — ลูกค้าส่งของกลับ นำกลับเข้าสต็อก

InventoryReturnStockInPort ทำงานตอนเรียก PATCH /wh/returns/:id/complete เมื่อผลตรวจสอบสรุปว่าให้นำกลับเข้าสต็อก (Restock) เส้นทางนี้เปิด lot ใหม่ ไม่ได้ reverse lot เดิม

lot ใหม่ สถานะ Available
→
2
wms.stock_balances INSERT
แถวใหม่ on_hand = qty
→
3
wms.stock_movements INSERT
movement_type = 'return_in'
รายละเอียดการเขียน — คืนสต็อก (ทั้ง 2 เส้นทาง)
เส้นทางTableคำสั่งผลลัพธ์
3awms.stock_balancesUPDATEreserved = GREATEST(0, reserved - qty), ไม่แตะ on_hand
3awms.stock_reservationsUPDATEstatus = 'released' — ไม่ทำอะไรถ้า status เดิมเป็น committed หรือ released อยู่แล้ว
3bwms.inventory_lotsINSERTเปิด lot ที่ผ่านการตรวจเกรดจากการคืนของ
3bwms.stock_balancesINSERTแถว balance ใหม่ผูกกับ lot ใหม่ on_hand = qty
3bwms.stock_movementsINSERTmovement_type = 'return_in', to_location_id = location รับคืน (RTN-IN)
3b ไม่แตะ wms.stock_reservations เลย — เพราะตอนที่ return เสร็จสมบูรณ์ การจองของออเดอร์นั้นถูกปล่อยหรือ commit ไปแล้วตั้งแต่ช่วงก่อนหน้าของ order lifecycle ทั้งสองเส้นทางนี้ไม่ตัดกัน
