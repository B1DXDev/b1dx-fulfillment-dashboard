เคส: Shop A กับ Shop B ใช้ platform_sku_code เดียวกันแต่หมายถึงคนละสินค้า — ตามข้อ test #4 ของ MATCH-WORKER-01

สรุปสั้น: คำถามหลักคือ "พิมพ์จากรายการไหน" — คำตอบคือ ทุกเอกสารที่พิมพ์ (Picking Slip / Shipping Label) อ่านจาก order_items โดยตรง ไม่เคย query sku_mappings ตอนพิมพ์เลย — sku_mappings ถูกใช้แค่ตอน resolve ครั้งแรก (auto-match หรือ manual match) แล้วผลลัพธ์ (matched_product_id) ถูกเขียน กลับลง order_items ทันที ทุก flow ถัดไปจึงไม่ต้อง join กับ sku_mappings อีก

3. orders + order_items — ผลลัพธ์หลัง auto-match resolve แล้ว

SELECT o.order_no, o.oms_shop_id, oi.sku_code, oi.matched_product_id, p.name
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.matched_product_id
WHERE oi.sku_code = 'SP-001';

4. รายการที่พิมพ์จริง — อ่านจาก order_items ตรงๆ

ทั้ง Picking Slip และ Shipping Label ไม่ query sku_mappings เลย เพราะ matched_product_id ถูก resolve และเขียนลง order_items ไปตั้งแต่ก่อนพิมพ์แล้ว

ผลลัพธ์ปฏิบัติ:

  • ORD-1001 (Shop A) → พิมพ์ picking slip ระบุ "กระเป๋าหนัง Tote"
  • ORD-2005 (Shop B) → พิมพ์ picking slip ระบุ "รองเท้าผ้าใบ Canvas"

แม้ sku_code ทั้งสอง order จะเป็น SP-001 เหมือนกันเป๊ะ พนักงานคลังจะไม่มีทางหยิบผิดสินค้า เพราะ resolve ที่ถูกต้อง (แยกตาม shop_id) เกิดขึ้นและถูกบันทึกไว้ล่วงหน้าแล้ว ก่อนถึงขั้นตอนพิมพ์

5. matched_product_id vs sku_mappings — คนละหน้าที่ คนละอายุการใช้งาน

order_items.matched_product_id

  • อยู่ใน order item แต่ละแถว
  • ผูกกับ 1 order item เดียวเท่านั้น
  • เป็น สำเนาที่ freeze ไว้ ตอน resolve เสร็จ
  • ใช้ตลอดไป แต่เฉพาะ order ใบนั้น
  • ทุกอย่างที่ทำกับ order ใบนั้น (Pick/Pack/พิมพ์) อ่านจากตรงนี้

sku_mappings

  • ตารางแยกต่างหาก ไม่ผูกกับ order ใดๆ
  • Key คือ (shop_id, platform_sku_code)
  • เป็น ต้นทางของกฎ (source of truth)
  • ใช้ซ้ำได้กับ order ในอนาคตทุกใบ ที่ SKU เดิม/ร้านเดิม
  • Auto-match service อ่านตารางนี้ตอน sync order ใหม่เข้ามา
เทียบกับชีวิตจริง: sku_mappings คือ สมุดโน้ตแปะหน้าคลัง เขียนไว้ว่า "ป้าย SP-001 จากซัพพลายเออร์ A = กระเป๋าหนัง Tote" — เขียนครั้งเดียว ใช้ดูได้ทุกครั้งที่ของ SP-001 จากซัพพลายเออร์ A เข้ามาใหม่ ส่วน matched_product_id คือ ป้ายที่แปะบนกล่องพัสดุใบนั้นโดยเฉพาะ — หลังเปิดสมุดโน้ตดูแล้วรู้ว่าคือกระเป๋า ก็เขียน "กระเป๋าหนัง Tote" แปะไว้บนกล่องนั้นเลย พนักงานคนต่อไปที่มาหยิบของ ไม่ต้องเปิดสมุดโน้ตอีก อ่านจากป้ายบนกล่องได้ทันที

ทำไมต้องมีทั้งคู่ ไม่ใช้แค่ตัวเดียว

ถ้ามีแค่ sku_mappings อย่างเดียว (ไม่มี matched_product_id): ทุกครั้งที่พิมพ์ picking slip ต้อง join กับ sku_mappings ใหม่ทุกครั้ง และถ้า user แก้ mapping ทีหลัง order เก่าที่พิมพ์ไปแล้วจะเปลี่ยนสินค้า ตามไปด้วยแบบไม่ควบคุม — อันตราย เพราะ order ที่แพ็คไปแล้วไม่ควรเปลี่ยนสินค้าย้อนหลัง

ถ้ามีแค่ matched_product_id อย่างเดียว (ไม่มี sku_mappings): ทุก order ใหม่ที่เข้ามาต้องให้ user manual match ซ้ำทุกครั้ง แม้จะเป็น SKU เดิมจากร้านเดิมที่เพิ่ง match ไปเมื่อวาน — ไม่มี auto-match เลย

sku_mappings เป็น ต้นทาง ของค่า ส่วน order_items.matched_product_id เป็น สำเนาที่ freeze ไว้ — พอ resolve เสร็จแล้วสองตัวนี้แยกอิสระจากกันทันที แก้ sku_mappings ทีหลังไม่กระทบ order เก่าที่ resolve ไปแล้ว มีผลแค่กับ order ใหม่ ที่จะ sync เข้ามาต่อจากนี้เท่านั้น
