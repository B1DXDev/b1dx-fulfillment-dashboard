1. Executive Summary

3กลุ่ม Flow หลัก: Happy Path, Cancel Flow, Return Flow

ข้อสรุปสำคัญ: PROCESSED ไม่ใช่ "ขนส่งมารับพัสดุแล้ว" — เป็นแค่จุดที่ ร้านกดยืนยันจัดส่ง (เรียก ship_order API) โดย TrackingNo อาจยังไม่ออก พนักงานขนส่งมารับพัสดุจริงคือขั้นถัดไป (SHIPPED) และ RETRY_SHIP แตกออกจาก READY_TO_SHIP โดยตรง (3PL รับพัสดุไม่สำเร็จ) ไม่ใช่ post-dispatch delivery failure — สองจุดนี้เคยทำให้ FF-SYNC-037 ตัดสินใจ OMS mapping ผิดในรอบแรก (ดู § Known Gaps)

3. Status Flow

3.1 Happy Path

UNPAID ↓ ① ลูกค้ายืนยันชำระเงินสำเร็จ READY_TO_SHIP ↓ ④ ร้านกดจัดส่ง — เรียก ship_order API (TrackingNo อาจยังไม่ออก) PROCESSED ↓ ⑥ พนักงานขนส่งมารับพัสดุจริง + มีเอกสารจัดส่งแนบ SHIPPED ↓ ผู้ซื้อยืนยันได้รับสินค้า (หรือ auto-confirm) TO_CONFIRM_RECEIVE ↓ COMPLETED

3.2 Retry-Ship Flow (pickup failure — ไม่ใช่ post-dispatch failure)

READY_TO_SHIP ↓ ⑦ 3PL เข้ารับพัสดุไม่สำเร็จ ต้องนัดรับใหม่ RETRY_SHIP ↓ นัดรับใหม่สำเร็จ (วนกลับเข้าจุดเดิม) READY_TO_SHIP ← กลับเข้า flow ปกติ ยังไม่เคย "ออกจากร้าน" จริง

3.3 Cancel Flow

READY_TO_SHIP / PROCESSED ↓ ② ③ ผู้ซื้อ/ผู้ขายขอยกเลิก, หรือร้านไม่จัดส่งทันเวลา (auto-cancel) IN_CANCEL (อยู่ระหว่างขอยกเลิก) ↓ CANCELLED SHIPPED ↓ ⑤ พัสดุสูญหายระหว่างจัดส่ง — Shopee auto-cancel CANCELLED (ทุกสถานะก่อน SHIPPED) ↓ ⑨ ผู้ซื้อขอยกเลิก ต้องรอผู้ขายอนุมัติ IN_CANCEL ├─ ผู้ขายปฏิเสธ → กลับสถานะเดิมก่อนขอยกเลิก └─ ผู้ขายอนุมัติ/เพิกเฉย → CANCELLED

3.4 Return Flow

SHIPPED ↓ ⑧ ผู้ซื้อส่งคำขอคืนสินค้า/คืนเงิน TO_RETURN (อยู่ระหว่างดำเนินการ — ยังไม่ terminal) ↓ อนุมัติคำขอคืนแล้ว (มีข้อพิพาท → เข้ากระบวนการไกล่เกลี่ยแยกก่อนปิดจบ) COMPLETED

5. Known Gaps (pre-existing — นอกขอบเขต FF-SYNC-037)

⚠️
READY_TO_SHIP / PROCESSED / RETRY_SHIP รวมอยู่ที่ OMS 490 เดียวกัน

ตาม flow จริง PROCESSED ขยับหน้าไปกว่า READY_TO_SHIP/RETRY_SHIP หนึ่งขั้น (ร้านกดเรียกขนส่งไปแล้ว) แต่ OMS ยังไม่มี substate แยก ops จึงมองจาก OMS ไม่เห็นความต่างระหว่าง "ยังไม่กดอะไรเลย" กับ "กดเรียกขนส่งแล้ว รอ 3PL มารับ" — ถ้าต้องการแยก ต้องเพิ่ม OMS status code ใหม่ (เช่น ระหว่าง 490-500) เป็นงานแยกต่างหาก

⚠️
TO_CONFIRM_RECEIVE → OMS 550 "OutForDelivery" ชื่อไม่ตรงความหมาย

TO_CONFIRM_RECEIVE คือ "รอผู้ซื้อยืนยันว่าได้รับสินค้าแล้ว" (ใกล้ COMPLETED) แต่ OMS enum ชื่อ OutForDelivery สื่อว่า "กำลังนำส่ง" — ตำแหน่งลำดับใน flow ยังถูกต้อง (อยู่ระหว่าง SHIPPED กับ COMPLETED) ไม่กระทบ business logic เพราะ OMS ไม่ได้ผูก action ตามชื่อ enum โดยตรง แต่เป็นจุดที่ทำให้สับสนตอนอ่านโค้ด

✅
[แก้แล้ว] RETRY_SHIP / TO_RETURN เคย mapping-miss เงียบ

ก่อน FF-SYNC-037 ทั้งสองสถานะไม่มี case ใน seeder เลย ตกไปที่ oms.orders_status_mapping_misses แบบ no-op (หลัง FF-SYNC-008 ไม่ fallback ไป 200 แต่ค้างสถานะเดิมเงียบๆ) — อันตรายเฉพาะเคส RETRY_SHIP เพราะออเดอร์จะดูเหมือนจัดส่งปกติทั้งที่ 3PL รับพัสดุไม่สำเร็จ ตอนนี้แก้แล้วตามตารางด้านบน
