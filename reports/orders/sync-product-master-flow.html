UPDATE...SELECT FOR UPDATE SKIP LOCKED เหมือน pattern เดียวกับ order sync worker

รันหลายงานพร้อมกัน (จำกัดจำนวน)

จำกัดด้วย SemaphoreSlim(MaxDegreeOfParallelism) (default 4) — แต่ละงานยิง HTTP call ของตัวเอง

โหลดข้อมูลสดจาก OMS DB ก่อนส่งจริง

Infrastructure/Persistence/Repositories/ProductDataRepository.cs:41

แปลง Payload ตาม Platform (Adapter Pattern)

แต่ละ IMarketplaceAdapter สร้าง body ของตัวเอง จากข้อมูลกลางชุดเดียวกัน (ProductPushPayload):

  • Shopee — payload แบบ update_item อิง tier_index
  • Lazada — nested Request.Product.Skus[] — spec บอกให้ normalize saleProp เป็นตัวเล็กแต่โค้ดยังไม่ทำ
  • TikTok — ตัด attribute ให้เหลือ 3 ตัว พร้อม log warning
Infrastructure/Adapters/{Shopee,Lazada,TikTok}/*Adapter.cs

ยิง Marketplace API — ทีละ SKU ไม่ batch

1 HTTP call ต่อ 1 SKU (ไม่ได้ใช้ bulk endpoint ที่บางแพลตฟอร์มรองรับ) · ไม่ 2xx → throw MarketplaceApiException · 2xx แต่ business code error (Shopee error!=0 / Lazada code!="0" / TikTok code!=0) → คืน AdapterResult(Success:false)

#ปัญหาผลกระทบอ้างอิง
1🔴 PlatformAttributes ว่างเปล่าเสมอTikTok 3-attribute cap / Shopee tier-index / Lazada saleProp ไม่เคยถูกส่งจริง — ทุก push วันนี้ผิดเงียบๆ โดยไม่มี error ให้เห็นProductDataRepository.cs:41
2Priority column ไม่ถูกใช้Spec ให้เรียงคิวตาม priority ก่อน created_at แต่โค้ดเรียงตาม created_at อย่างเดียว — งาน priority สูงไม่ได้ถูกหยิบก่อนจริงOutboxRepository.cs:27 vs contract §2
3ยังไม่มี rate limiterADR-012 ระบุว่า channel-sync-worker ควรมี local limiter แบบเดียวกับ omsorders.sync.worker แต่ grep ทั้ง repo ไม่พบ limiter class เลย — เสี่ยงโดน marketplace throttle ตอน sync พร้อมกันหลาย SKUADR-012 line 100 (design) — ยังไม่ implement
4Credential broker ยังไม่ต่อสายContract ระบุ flow ผ่าน OMS-broker HMAC แต่โค้ดยังดึง ShopAccessToken ตรงจาก payload_json — มี comment ในโค้ดเองว่า "until credential broker (PIM-WORKER-01) is wired"ChannelSyncService.cs:59-60
5Lazada saleProp ไม่ normalizeSpec ให้แปลงเป็นตัวพิมพ์เล็กก่อนส่ง แต่ LazadaAdapter ยังไม่ทำ — อาจทำให้ Lazada ปฏิเสธ payload บางกรณีLazadaAdapter.cs:51-70 vs spec §3
🔴 เร่งด่วนที่สุด: Gap #1 คือรากของปัญหาที่ทำให้ต้องสร้าง Product Reconciliation ทั้ง spec ขึ้นมา — ถ้าแก้ ProductDataRepository.GetAsync ให้คืนค่า attributes จริง ปัญหา drift ที่เกิดจาก push ผิดจะลดลงเยอะโดยไม่ต้องพึ่ง reconciliation คอยจับ
