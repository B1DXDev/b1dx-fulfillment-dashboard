ภาพรวม

PIM UI (CRUD บน Product/Variant) เป็นจุดเริ่มของ sync สองสาย ที่ สถาปัตยกรรมคนละแบบกันโดยสิ้นเชิง — internal sync ยังอยู่ในขั้น spec (0% code), ส่วน external sync ไปไกลกว่าที่คาดมาก คือ built แล้ว ~80% เหลือแค่ credential broker

สรุป 1 บรรทัด งานที่ "เดี๋ยววิเคราะห์" ในหัวข้อ 6 (Marketplace) จริงๆ แล้วสร้างไปเกือบหมดแล้ว — สิ่งที่ต้องแตกงานให้เบนซ์ต่อคือช่องโหว่เล็กจุดเดียว (credential broker) ไม่ใช่ระบบใหม่ทั้งหมด ส่วนงาน internal sync (หัวข้อ 4) กลับเป็นด้านที่ยังไม่มี implementation เลยสักบรรทัด
4

Internal Sync — Product OMS / WMS / ERP

อ้างอิง ADR-004 (Status: Proposed) และ product-master-distribution.md (Status: Draft v1.0) — ออกแบบละเอียดมากแล้ว (field contract, DDL, versioning) แต่ tasks/plans ยังไม่มี ticket P0a–P9 ตัวไหนถูกสร้างเลย แปลว่ายังไม่มีใครเริ่มเขียนโค้ดจริง

Track A วันนี้ vs Track B เป้าหมาย

เพราะ PIM กับ OMS ยังอยู่ oms_db เดียวกัน (ยังไม่ split DB) การ sync จึงยังไม่ต้องใช้ RabbitMQ — ใช้ EF SaveChanges interceptor เขียน projection table ใน transaction เดียวกันได้เลย (Track A) เมื่อ WMS/ERP มี DB แยกจริงในอนาคต ค่อยเปิด Track B (RabbitMQ topic exchange + relay + inbox ต่อ consumer)

ปลายทางสถานะสิ่งที่ยังขาด
4.1 OMS SPEC ONLY ตัว net-new ทั้งหมด: pim.aggregate_version, pim.outbox_message (คนละตัวกับ outbox_message เดิมที่ sync-worker ใช้ทำ order sync — คนละ bounded context ห้ามเอามาใช้ร่วม), SaveChanges interceptor, ตาราง oms.product_master/product_variant/product_variant_price, และ identity bridge (คอลัมน์ pim_variant_id บน OMS Product/SkuMapping เดิม — ตัดสินใจแล้วว่าทำแบบ soft-match แต่ยังไม่ implement)
4.2 WMS BLOCKED field ที่ WMS ต้องใช้ (barcode, dimensions_json, weight_grams, packaging_json) ไม่มีอยู่ใน PIM Variant domain วันนี้เลย ต้องเพิ่ม field เหล่านี้ก่อน ถึงจะเริ่ม P8 ได้
4.3 ERP SPEC ONLY + มี flow เดิมอยู่แล้ว ระวังสับสนทิศทาง — ดู diagram ถัดไป
จุดที่มักสับสน — ERP มี 2 flow คนละทิศทาง วันนี้ b1dx.omsorders.sync.worker มี ErpMasterSyncService ที่ sync ERP → OMS อยู่แล้วจริง (SyncUom → SyncProduct → SyncCustomers) แต่มันเขียนลงตาราง oms.product แบบเก่า (flat, ไม่มี variant) — คนละตารางกับ PIM domain ใหม่ ส่วนที่ spec 4.3 พูดถึงคือทิศตรงข้าม: PIM → ERP (ส่ง cost/tax/hs_code ออกไปให้ ERP ใช้ทำบัญชี) ซึ่งยังไม่มี code เลยสักบรรทัด
5

PIM UI แก้ไข SKU

นี่คือ prerequisite ของหัวข้อ 4 ทั้งหมด — ถ้าแก้ SKU ได้โดย domain ไม่รองรับ การ sync ทุกปลายทาง (OMS/WMS/ERP/Marketplace) จะ desync แบบเงียบๆ

สถานะ domain วันนี้ Variant.cs เป็น creation-only — Sku เป็น private setter ไม่มี mutation method, ไม่มี VariantSkuChanged event, ไม่มีตาราง sku_code_history เลย พูดสั้นๆ: วันนี้แก้ SKU ผ่าน API ไม่ได้จริง แม้ FE จะมีช่องให้พิมพ์ก็ตาม

งานนี้ตรงกับ ticket P2 ใน rollout plan ของ product-master-distribution.md §6 พอดี — กฎสำคัญคือ product_variant_id (GUID, immutable) เป็น join key เดียวที่ downstream ทุกระบบใช้ ส่วน sku_code เป็นแค่ label ที่ rename ได้โดยไม่พัง mapping

6

PIM Sync to Marketplace

ข่าวดี: ส่วนนี้สร้างไปแล้วเกือบหมด ใน repo แยกชื่อ b1dx-channel-sync-worker — คนละ repo กับ b1dx-marketplace-webhook (ตัวหลังทำแค่ inbound: ดึง order/product เข้ามา ไม่เคยส่งอะไรออกไปที่ marketplace)

6.1 Product Sync กับ 6.2 Variant Sync — จริงๆ ไม่ใช่สองระบบ Pipeline ที่มีอยู่เป็น ตัวเดียว variant-centric ไม่ได้แยก product-level กับ variant-level ออกจากกัน เพราะ product_variant_id คือ join key ของทุก sync — สิ่งที่ต่างกันคือ sync_type ในแต่ละ outbox row (product-sync / price-sync / stock-sync / content-sync ฯลฯ ตาม §4 ของ channel-sync spec) แนะนำอย่าแตก 6.1/6.2 เป็นสอง ticket แยก — จะกลายเป็นงานซ้ำ

ช่องโหว่จริงที่เหลืออยู่ — Credential Broker

ChannelSyncService.cs มี comment ยืนยันตรงๆ ว่า "Token still sourced from payload until credential broker (PIM-WORKER-01) is wired" — token OAuth ของแต่ละร้านถูกฝังไว้ใน payload_json ตอนเขียน outbox แทนที่จะขอ token สดจาก broker ตอน push จริง ปัญหา: ถ้า job ค้าง retry นาน (16 นาที) token อาจหมดอายุไปแล้ว และการฝัง secret ลง payload_json ก็ไม่ควรทำระยะยาว

Risk ที่ควร flag ให้ product owner

  • อัปเดต 2026-07-21ADR-004 เป็น "Accepted" แล้ว ผ่าน D3 + D4 — D3: RabbitMQ สำหรับ marketplace-channel-sync-merge (FF-PIM-003). D4 (เพิ่มเข้ามาวันเดียวกัน): internal sync (หัวข้อ 4) จะใช้ RabbitMQ ด้วย exchange เดียวกัน — reverse นิยาม Track A เดิม. แต่ทั้ง D3 และ D4 เป็น transport decision เท่านั้น — implementation จริงของ internal sync (pim.aggregate_version/pim.outbox_message/OMS-WMS-ERP read-model, P0a-P9) ยังไม่ reconcile กับ D4 และไม่ใช่ scope ของ FF-PIM-003 อย่าอ่านว่า "D4 approve แล้ว = เริ่ม P0a ได้เลย" — ต้องมีคน reconcile product-master-distribution.md ก่อน
  • Identity bridge ตัดสินใจแล้วแต่ยังไม่ implement — คอลัมน์ pim_variant_id บน OMS Product/SkuMapping (D2 ใน ADR-004) ยังไม่มีอยู่จริง จนกว่าจะสร้าง PIM กับ OMS legacy catalog จะแยกขาดจากกันต่อไป
  • Fan-out storm ยังไม่ benchmark — ADR ระบุว่า bulk price import / category re-assign อาจทำให้ event ยิงถล่ม ต้อง benchmark ก่อนเปิด relay จริง — อัปเดตเดิมวางแผนไว้ "ก่อนเปิด Track B" (P8/P9), หลัง D4 relevant ตั้งแต่ P1 เพราะ RabbitMQ เข้ามาเร็วขึ้นกว่าที่ D1 วางแผนไว้เดิม
  • ใหม่ 2026-07-21Naming collision risk ระหว่างสองความพยายาม — FF-PIM-003's pim_outbox_messages (flat, oms_db, marketplace-merge) กับ ADR-004's pim.outbox_message (schema-qualified, future PIM-own-DB, internal sync) เป็นคนละตารางที่ชื่อใกล้กันมาก — คนที่มาเริ่ม P0a/P1 ของ internal sync ในอนาคตต้องเลือกชื่อไม่ชนกัน (ดู ADR-004 § D3)
