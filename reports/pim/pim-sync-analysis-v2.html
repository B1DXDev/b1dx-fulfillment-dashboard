วิเคราะห์ flow ของ PIM CRUD → Sync สองทิศทาง: internal (OMS/WMS/ERP) และ external (Marketplace) — ทั้งสองทิศทางแชร์ transport เดียวกัน (RabbitMQ, ADR-004 D3+D4) แต่คนละ implementation status

ภาพรวม

PIM UI (CRUD บน Product/Variant) เป็นจุดเริ่มของ sync ที่ปลายทางต่างกัน (Marketplace, OMS, WMS, ERP) แต่ ตอนนี้ transport เป็นท่อเดียวกันหมด — outbox → RabbitMQ exchange b1dx.pim.product → แยก route ด้วย queue/routing-key เท่านั้น ความต่างที่แท้จริงอยู่ที่ ใครสร้างปลายทางไปถึงไหนแล้ว ไม่ใช่สถาปัตยกรรมคนละแบบเหมือน v1

สรุป 1 บรรทัด Transport (outbox + RabbitMQ) เป็นเรื่องเดียว กำลังสร้างโดย FF-PIM-003 (assigned sompon-benz, ครอบเฉพาะ marketplace queues) — ส่วนปลายทาง ต่างกันไกลมาก: marketplace (§6) built แล้ว ~80% เหลือ credential broker consumption, ส่วน internal sync read-model เอง (§4.1-4.3) ยังเป็น spec-only 0% code แม้ transport จะ approve แล้วก็ตาม
4

Internal Sync — Product OMS / WMS / ERP

อ้างอิง ADR-004 (Status: Accepted — D3 + D4, transport เท่านั้น) และ product-master-distribution.md (Status header: Accepted, แต่เนื้อหายังไม่ reconcile กับ D4) — field contract/DDL/versioning ออกแบบละเอียดมากแล้วตั้งแต่ก่อน D4 แต่ tasks/plans ยังไม่มี ticket P0a–P9 ตัวไหนถูกสร้างเลย แปลว่ายังไม่มีใครเริ่มเขียนโค้ดจริง

อย่าอ่านผิด — D4 approve แค่ transport ADR-004 D4 (2026-07-21) ตัดสินว่า internal sync จะใช้ RabbitMQ exchange เดียวกับ marketplace-merge — แต่นี่คือ decision เรื่องtransportเท่านั้น ไม่ใช่การ greenlight ให้เริ่ม P0a ทันที product-master-distribution.md (versioning, identity bridge, consistency model, DDL, fan-out benchmark timing) ยังเขียนด้วยสมมติฐาน Track A เดิม (ก่อน D4) ต้องมีคน reconcile เอกสารนั้นก่อนเริ่ม implement จริง

สถาปัตยกรรม transport วันนี้ (หลัง D3+D4)

เส้นแบ่งเดิมของ v1 (Track A = same-DB no-broker, Track B = split-DB with-broker) ไม่ใช้บนมิติ transport แล้ว — RabbitMQ ถูกนำมาใช้ตั้งแต่วันนี้ผ่าน exchange เดียวกับ §6 (diagram 0) แม้ PIM+OMS จะยังอยู่ oms_db เดียวกัน (ยังไม่ split DB จริง) สิ่งที่ยังต่างกันคือ DB topology ไม่ใช่ transport

ปลายทางTransportConsumer → DB ระบบสิ่งที่ยังขาด
4.1 OMS DECIDED (D4) SPEC ONLY ตัว net-new ทั้งหมดของฝั่ง consumer: versioning column, SaveChanges/consumer upsert เขียนเข้า oms_db (DB ระบบ OMS), identity bridge (pim_variant_id บน OMS Product/SkuMapping — ตัดสินใจ soft-match แล้วแต่ยังไม่ implement, D2)
4.2 WMS DECIDED (D4) BLOCKED field ที่ WMS ต้องใช้ (barcode, dimensions_json, weight_grams, packaging_json) ไม่มีอยู่ใน PIM Variant domain วันนี้เลย ต้องเพิ่มก่อนถึงจะเริ่มได้ ไม่เกี่ยวกับ transport
4.3 ERP DECIDED (D4) SPEC ONLY + มี flow เดิมคนละทิศ ระวังสับสนทิศทาง — ดู diagram ถัดไป
จุดที่มักสับสน — ERP มี 2 flow คนละทิศทาง วันนี้ b1dx.omsorders.sync.worker มี ErpMasterSyncService ที่ sync ERP → OMS อยู่แล้วจริง (SyncUom → SyncProduct → SyncCustomers) แต่มันเขียนลงตาราง oms.product แบบเก่า (flat, ไม่มี variant) — คนละตารางกับ PIM domain ใหม่ ส่วนที่ §4.3 พูดถึงคือทิศตรงข้าม: PIM → ERP (ส่ง cost/tax/hs_code ออกไปให้ ERP ใช้ทำบัญชี) ซึ่งยังไม่มี code เลยสักบรรทัด
5

PIM UI แก้ไข SKU

นี่คือ prerequisite ของหัวข้อ 4 ทั้งหมด — ถ้าแก้ SKU ได้โดย domain ไม่รองรับ การ sync ทุกปลายทาง (OMS/WMS/ERP/Marketplace) จะ desync แบบเงียบๆ

สถานะ domain วันนี้ (ไม่เปลี่ยนจาก v1) Variant.cs เป็น creation-only — Sku เป็น private setter ไม่มี mutation method, ไม่มี VariantSkuChanged event, ไม่มีตาราง sku_code_history เลย พูดสั้นๆ: วันนี้แก้ SKU ผ่าน API ไม่ได้จริง แม้ FE จะมีช่องให้พิมพ์ก็ตาม

งานนี้ตรงกับ ticket P2 ใน rollout plan ของ product-master-distribution.md §6 (rollout numbering เดิม ยังไม่ renumber ตาม D4) — กฎสำคัญคือ product_variant_id (GUID, immutable) เป็น join key เดียวที่ downstream ทุกระบบใช้ ส่วน sku_code เป็นแค่ label ที่ rename ได้โดยไม่พัง mapping

6

PIM Sync to Marketplace

ส่วนนี้สร้างไปแล้วเกือบหมด ใน repo แยกชื่อ b1dx-channel-sync-worker — คนละ repo กับ b1dx-marketplace-webhook (ตัวหลังทำแค่ inbound) กำลัง migrate transport ไป RabbitMQ ผ่าน FF-PIM-003 (ดู §9) — pipeline ด้านล่างคือสถานะวันนี้ (DB-polling) ก่อน migration เสร็จ

6.1 Product Sync กับ 6.2 Variant Sync — จริงๆ ไม่ใช่สองระบบ Pipeline ที่มีอยู่เป็น ตัวเดียว variant-centric ไม่ได้แยก product-level กับ variant-level ออกจากกัน เพราะ product_variant_id คือ join key ของทุก sync — สิ่งที่ต่างกันคือ sync_type ในแต่ละ outbox row (product-sync / price-sync / stock-sync / content-sync ฯลฯ ตาม §4 ของ channel-sync spec) แนะนำอย่าแตก 6.1/6.2 เป็นสอง ticket แยก — จะกลายเป็นงานซ้ำ

ช่องโหว่จริงที่เหลืออยู่ — Credential Broker

ChannelSyncService.cs:59 มี comment ยืนยันตรงๆ ว่า "Token still sourced from payload until credential broker (PIM-WORKER-01) is wired" — token OAuth ของแต่ละร้านถูกฝังไว้ใน payload_json ตอนเขียน outbox แทนที่จะขอ token สดจาก broker ตอน push จริง (verify สดในโค้ด 2026-07-21 — comment ยังอยู่ไม่เปลี่ยน) ปัญหา: ถ้า job ค้าง retry นาน (16 นาที) token อาจหมดอายุไปแล้ว และการฝัง secret ลง payload_json ก็ไม่ควรทำระยะยาว

Risk ที่ควร flag ให้ product owner

  • Transport decided ≠ implementation ready — ADR-004 D3+D4 อนุมัติ RabbitMQ ทั้ง §4 และ §6 แล้ว แต่ internal-sync consumer/read-model (§4.1-4.3) ยังเป็น spec-only 0% code และ product-master-distribution.md ยังไม่ reconcile กับ D4 — อย่าอ่านว่า "D4 approve แล้ว = พร้อม build"
  • Naming collision — pim_outbox_messages (Epic #1050, flat, oms_db) กับ pim.outbox_message (product-master-distribution.md, schema-qualified, future) เป็นคนละตารางที่ชื่อใกล้กันมาก ต้องแก้ก่อนสร้างตารางหลัง
  • Identity bridge ตัดสินใจแล้วแต่ยังไม่ implement — คอลัมน์ pim_variant_id บน OMS Product/SkuMapping (D2 ใน ADR-004) ยังไม่มีอยู่จริง
  • Fan-out storm ยังไม่ benchmark — เดิมวางแผนไว้ "ก่อนเปิด Track B" (P8/P9), หลัง D4 relevant ตั้งแต่ P1 เพราะ RabbitMQ เข้ามาเร็วขึ้นกว่าที่วางแผนไว้เดิม
  • ChannelMappingEnabled publisher flag — ต้องรอ 003c — เปิด flag นี้ก่อนมี consumer จะทำให้ legacy DB-poll worker แย่ง row ไม่ได้ (publisher ชนะ race) และ marketplace sync จะหยุดทำงานเงียบๆ โดยไม่มี error (ดู pim-product-outbox-sync.md § 12.3)
